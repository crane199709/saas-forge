# 文件保留期采用引用检查与两阶段删除，未实现引用检查不自动删除

Storage Purpose 增加服务声明的 `retentionDays`，Tenant 与 Operator 不能修改；到期只把文件记录标记为失效，7 天宽限期后才删除存储对象并释放配额。删除前必须经引用检查：SDK 提供 `FileReferenceChecker` SPI，由业务服务用自己的库查询仍被引用的对象；未实现检查器、检查异常或超时都按“有引用”处理，跳过删除并告警。逻辑删除的业务行仍算引用，因为 Restore 可能把它恢复。

保留期的目标是存储卫生——清理未确认上传、被替换、导入失败和业务行已不存在的孤儿文件；被业务数据引用的文件不因保留期删除。v1 不引入 Legal Hold，但 `forge_storage_object` 的状态设计为可扩展枚举，预留合规冻结状态。

## Considered Options

- 不检查引用，按用途到期即删：会删掉仍被业务数据引用的文件，业务页面出现附件缺失。
- 由 Tenant 按用途配置保留期：破坏 Storage Purpose“服务声明、Tenant 不能修改”的既有定义。
- 引入 Legal Hold：需要额外的权限、流程与审计，目前没有客户需求。

## Consequences

- `forge_storage_object` 增加生命周期状态与保留截止时间，删除从“立即物理删除”改为两阶段。
- 清理任务在各业务服务内按 Tenant 运行，平台不跨库删除。
- 配额在物理删除时释放，宽限期内仍计入已用容量。
- 若以后需要合规删除（即使被引用也删），增加 Purpose 级 `compliance` 模式，而不是改变默认语义。
