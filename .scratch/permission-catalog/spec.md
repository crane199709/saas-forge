# 权限目录契约规格

Status: resolved

术语以 [GLOSSARY.md](../../GLOSSARY.md) 为准：Permission Code、Resource Manifest、Permission Catalog。本规格不单独记录 ADR，因为目录是构建期快照，移除或替换不影响运行时语义。

## 问题陈述

Permission Code 分散在各服务的 Resource Manifest、注解和 IAM 的权限表里。外部 Sub-App、前端与集成方没有一份经过审查的完整清单：

- 新权限码的命名与动作词不统一，只能靠评审发现；
- 外部 Sub-App 无法在开发期检查自己的权限码是否与平台冲突；
- 前端无法引用一份稳定的权限清单做按钮与路由控制；
- 权限码变更没有 CI 门禁，漂移只能等到运行时暴露。

## 解决方案

生成并校验确定性的权限目录：

- 每个服务在构建时输出自己的 Manifest JSON，核心 IAM/Platform 也输出同格式清单；
- 根脚本合并、排序、去重，生成 `permission-catalog.json` 并入库；
- CI 重新生成并与入库文件做字节级比较，不一致就失败；
- 动作词白名单校验新权限码，历史例外清单显式登记；
- 前端、外部 Sub-App 与文档消费该文件；运行时权威仍是 IAM 的权限记录。

## 用户故事

1. 作为平台管理员，我想看到全平台 Permission Code 的完整清单，以便审查命名与归属。
2. 作为平台管理员，我想让新权限码必须使用批准的动作词，以便命名一致。
3. 作为平台管理员，我想让违反动作词的存量编码进入例外清单，以便逐步收敛而不阻塞交付。
4. 作为外部 Sub-App 开发者，我想引用一份稳定的权限目录，以便开发期检查权限码冲突。
5. 作为前端开发者，我想从目录生成按钮权限常量，以便不手写字符串。
6. 作为贡献者，我想用一条命令重新生成目录，以便提交前修正漂移。
7. 作为 CI，我想在目录与代码不一致时失败，以便阻止漂移合并。
8. 作为审计员，我想让目录包含已下线（inactive）的权限码，以便追溯历史授权。
9. 作为业务服务开发者，我想让目录自动包含我声明的权限码，以便不额外维护列表。
10. 作为平台管理员，我想让核心 IAM/Platform 的权限码也进入目录，以便目录完整。

## 实现决策

- 每个业务服务在构建或测试阶段用现有 Manifest 生成能力输出 `resource-manifest.json`；核心 IAM/Platform 增加同格式的导出入口。
- 根脚本读取各服务清单，合并为一份目录，字段至少包含 `schemaVersion`、`functions`、`actions` 或等价的扁平结构，按稳定键排序。
- 目录包含 active 与 inactive 权限码，并标注服务、名称与分组；不包含时间戳、构建路径或运行期数据。
- 目录文件入库到 `docs/contracts/permission-catalog.json`，UTF-8、LF、末尾换行。
- CI 重新生成到临时位置并与入库文件逐字节比较；不一致时提示运行生成命令。
- 动作词白名单校验权限码的动作段；存量例外写入显式清单，只允许新增违规不被引入。
- 运行时仍以 IAM 的 `permission` 表与 Resource Manifest 为准；目录不是第二事实源。
- 外部服务的权限码不在仓内目录中，由 IAM 在上报时保证全局唯一；目录只覆盖仓内服务与核心。
- 不新增运行时目录 API；如需，后续单独设计。

## 测试决策

- 好的测试只验证外部行为：生成文件的内容与顺序、CI 比较结果、动作词校验结果；不直接断言合并脚本的内部函数。
- 首选接缝是“生成命令 + 入库文件”这一对：用同一命令生成两次，断言字节一致；再故意改一个权限码，断言校验失败。
- Manifest 收集沿用现有 `ResourceManifestCollector` 的测试接缝，不新建清单格式。
- 参考现有测试：`ResourceManifestCollectorTest`、`ResourceManifestTest`、`ManifestReporterTest`。
- CI 接线在仓库工作流中验证，不在单测里模拟。

## 不在范围

- 运行时权限目录 API。
- 外部服务权限码的仓内收录。
- 批量重命名现存权限码。
- 权限码与角色、套餐的关联分析。
- 目录的可视化页面。

## 补充说明

- 目录是“可审查快照”，不是授权数据源；删除某个权限码仍走 IAM 的停用流程。
- 动作词表先覆盖现有常用动作，新增动作需要更新白名单并说明理由。
- 外部 Sub-App 若需要冲突检查，使用发布后的目录文件；平台不承诺目录包含尚未上报的外部服务。
