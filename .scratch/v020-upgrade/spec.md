# v0.2.0 脚手架交付与已有工程升级

Status: ready-for-agent

## Problem Statement

`0.1.0` 与 `0.2.0` 均不是产品正式版。本文中的版本发布指制品发布；“已发布”“候选”“待发布”仅区分制品状态。

平台准备发布版本 `v0.2.0`。新版本包含 SDK、脚手架、开发规范、接口入口和前端主题等变化，但已有 Business Service 与 Sub-App 不会随脚手架发布自动更新。维护者需要知道哪些依赖和生成文件必须调整，如何保留已有业务代码、配置和数据，以及怎样证明升级后的工程仍能正常接入平台。

当前发布流程已有制品消费、新建工程模板冒烟和主链路验证。它们能够证明当前制品可以用于新建工程，不能直接证明已发布的 `0.1.0` 工程或已接入的业务工程能够升级。升级要求分散在变更日志与接入指南中，尚缺集中、可复现的升级路径和对应发布证据。

本次需要同时解决新版工程交付与存量工程升级，并在版本发布前完成验证，避免业务团队在使用已发布制品后才发现升级遗漏。

## Solution

为 `v0.2.0` 交付配套的后端 archetype、前端 sub-app-kit、新版参考工程与统一升级说明。业务工程通过更新依赖、审阅并合并必要模板差异完成升级，保留自有业务代码、配置和已执行迁移。

通用升级路径覆盖 `0.1.0 → 0.2.0`，另对 `lowcode`、`ai-platform` 的实际使用版本完成升级。平台 CI 持续验证已发布旧版工程的升级；两个试点分别在自己的升级分支完成实际改动与隔离验收。默认脚手架与 IO、storage 可选能力分别提供升级证据。

先将固定候选提交的制品打包到隔离的临时 Maven/npm 仓库，供自动测试和两个试点消费。新建、通用升级、可选能力和试点验收均通过后，交付发布准备结果；随后另按发布流程执行版本发布与环境切换，并从目标制品仓库进行只读消费复验。

## User Stories

1. 作为平台维护者，我希望新版脚手架能从候选制品生成可运行的 Business Service 和 Sub-App，以便确认新接入工程使用的是完整、配套的交付物。
2. 作为已有 Business Service 的维护者，我希望获得 `0.1.0 → 0.2.0` 的升级步骤，以便评估并完成服务升级。
3. 作为已有 Sub-App 的维护者，我希望获得前端依赖、构建配置和宿主接入的升级步骤，以便升级后仍能被 Shell App 正常加载。
4. 作为 lowcode 的维护者，我希望按工程实际基线完成升级和验收，以便确认通用升级说明能支撑真实业务。
5. 作为 ai-platform 的维护者，我希望按工程实际基线完成升级和验收，以便确认已有快照接入结果可以迁移到 `0.2.0`。
6. 作为业务开发者，我希望明确区分平台依赖版本、业务工程自身版本和 Resource Manifest 版本，以便调整正确的版本而不改变无关业务标识。
7. 作为业务开发者，我希望通过新版临时参考工程审阅模板差异，以便准确合入生成文件的必要变化。
8. 作为业务开发者，我希望已有业务代码和业务领域模型得到保留，以便升级不覆盖已完成的业务开发。
9. 作为业务工程维护者，我希望在合并新版配置时保留项目自定义项，以便升级不会丢失本工程的环境和运行约定。
10. 作为数据库维护者，我希望保留已经执行的 Flyway 迁移，以便已有数据库的迁移历史仍然有效。
11. 作为 Business Service 的维护者，我希望通过新增迁移补齐 SDK 所需的表结构变化，以便已有数据可以继续使用。
12. 作为接入 IO 的维护者，我希望验证相关增量迁移及升级后的导入导出行为，以便升级不会破坏已有任务和数据。
13. 作为接入 storage 的维护者，我希望验证相关增量迁移及已有文件的业务行为，以便升级后已有文件仍按约定可用。
14. 作为尚未接入可选能力的维护者，我希望升级说明按实际使用能力列出步骤，以便不引入无关依赖、表或配置。
15. 作为 Business Service 的维护者，我希望知道新版本检查规则和必配项的变化，以便在部署前发现构建或启动问题。
16. 作为业务开发者，我希望同步更新工程级 Agent 约定与规范副本，以便开发者和 Agent 使用与依赖版本相符的规则。
17. 作为 Sub-App 的维护者，我希望 SDK、UI、kit 与共享依赖版本对齐目标 Shell，以便开发和联邦加载使用一致的契约。
18. 作为 Sub-App 的维护者，我希望清楚处理统一接口入口的变化，以便升级后业务请求仍能通过网关到达正确服务。
19. 作为 Sub-App 的开发者，我希望升级后独立开发宿主仍能正常工作，以便继续本地开发和调试。
20. 作为 Sub-App 的维护者，我希望验证构建产物实际挂载到配套 Shell 的结果，以便确认独立开发成功之外的运行时接入行为。
21. 作为 Sub-App 的维护者，我希望区分继承宿主主题与业务页面写死样式的差别，以便正确处理主题和规范升级。
22. 作为环境维护者，我希望明确同一环境需要配套升级的组件，以便安排协调切换。
23. 作为平台维护者，我希望旧版基线来自已发布制品，以便升级测试对应业务团队真实拿到的版本。
24. 作为平台维护者，我希望候选制品在版本发布前可供消费，以便先完成升级验证再发布版本制品。
25. 作为 CI 维护者，我希望通用升级验证可重复运行并进入发布质量门，以便后续候选变化能及时暴露升级问题。
26. 作为本地验证者，我希望使用与 CI 相同的验证入口，以便复现和修复失败。
27. 作为评审者，我希望能够核对候选提交、制品摘要、试点基线和验收结果，以便判断证据是否对应当前候选版本。
28. 作为平台维护者，我希望候选内容变化后重新验证受影响部分，以便避免继续使用过期验收结果。
29. 作为升级执行者，我希望验证失败时保留可定位的问题信息，以便补齐改动和修正升级说明。
30. 作为发布维护者，我希望任何必要路径缺少证据或未通过时不能宣称发布就绪，以便让发布结论与实际验证一致。
31. 作为发布维护者，我希望版本发布后从目标制品仓库只读消费制品，以便确认最终仓库中的制品可用。
32. 作为两个试点的维护者，我希望实际升级发现被补进通用清单，以便其他业务工程减少重复排查。
33. 作为环境维护者，我希望试点升级验收使用隔离环境，以便本次发布准备不会操作正在使用的共享数据。

## Implementation Decisions

1. **交付范围与责任**
   - 平台负责两套脚手架、规范分发、参考工程、升级清单、可重复验证入口与发布质量门的必要调整。
   - 本次包含 lowcode、ai-platform 两个仓库的实际升级。在各自升级分支合并必要改动、完成隔离验收，再将发现回填平台升级清单。
   - 各业务仓库拥有其业务代码、自定义配置与数据库迁移历史。升级以更新依赖和审阅差异为方式，不自动覆盖已有工程。

2. **支持基线与版本含义**
   - 通用支持范围为 `0.1.0 → 0.2.0`。两个试点按实施时核对的实际提交、依赖和迁移记录建立基线，不将它们统一假定为已发布的 `0.1.0` 工程。
   - 平台依赖版本与业务工程自身版本分别维护；Resource Manifest 版本依其声明是否变化调整，不随依赖升级机械递增。
   - 默认工程、Sub-App、storage 的旧版输入使用实际已发布制品，候选输入使用实际打包制品。IO 在 `0.1.0` 发布时尚不存在，按用户补充确认使用可核对历史提交的 IO 源码构建未发布基线，明确区分其来源。保留来源、版本与摘要，隔离本机 Forge 制品缓存对结果的影响。

3. **脚手架与工程文件升级**
   - 检查 forge-service-archetype、sub-app-kit 的打包内容、配套版本和规范分发，补齐本次发布所需差异。
   - Business Service 对照同版本参考工程，合并父 POM/SDK、检查插件、Wrapper、配置、规范及测试骨架的必要变化；保留业务工程自身标识和业务实现。
   - Sub-App 对照同版本参考工程，合并依赖、构建与检查配置、开发宿主、启动脚本、规范及接入说明的必要变化；保留业务页面与路由语义。
   - 默认脚手架保持默认 starter 的必需项，可选 IO、storage 继续按需接入。

4. **前端配套与接口契约**
   - 同一环境的 Shell App、前端 SDK、UI、kit 和受影响 Sub-App 配套升级，共享依赖按配套版本表精确对齐。
   - 沿用统一接口入口契约：SDK 为浏览器业务请求添加 `/api`，Shell 剥离后转发网关；业务源码中的服务路径、网关服务前缀及 `/iam` 认证路径保持既有含义。已有 Sub-App 移除 `apiPrefixes`，环境配置同步处理已移除的逐服务代理项。
   - 不承诺 `0.1.0` 与 `0.2.0` 混合运行。受影响 Sub-App 尚未完成升级时，该环境先不单独切换新版 Shell，按环境协调切换。
   - 遵守既有 Theme Token 契约，升级配套宿主与依赖、检查主题继承；已有写死样式按实际差异处理，不承诺自动迁移。

5. **数据库与数据保留**
   - 已执行的 Flyway 迁移保持原样，不能用新版脚手架合并后的初始迁移替换旧工程历史。
   - 根据实际使用的 SDK、现有结构和迁移记录新增所需增量迁移，不重复应用已经完成的升级。
   - 默认工程与 IO、storage 分别验证。可选能力使用独立样例，升级前写入代表性数据，升级后检查原数据可用及相关业务行为。
   - 本规格不引入用于升级的生产运行时 API 或业务表；实际结构变化复用所用 SDK 已有的升级要求。

6. **候选制品与版本发布衔接**
   - 固定候选提交，将配套制品打包到隔离临时 Maven/npm 仓库，供 CI 和两个试点消费，记录候选版本及制品摘要。
   - 新建工程、已发布旧版升级、IO/storage、两个试点均通过后，才可形成发布就绪结论。平台 CI 自动验证通用路径，试点验收作为本次发布证据，不将真实业务仓库整体并入平台测试套件。
   - 候选提交或制品内容发生变化后，识别影响范围并复验；影响两个试点的变化须更新对应试点证据。
   - 版本发布和环境切换另按现有发布流程执行。版本发布后复用只读消费能力验证目标仓库中的制品，不能将上传成功视为消费成功。

7. **升级说明与交付证据**
   - 集中说明支持起点、依赖版本、必改项、按能力选择的迁移、参考工程差异、执行与验证命令、成功判据和失败处理信息。
   - 明确列出必须合入的变化与按项目实际情况处理的变化，保留工程自定义内容。
   - 接入指南、规范分发、脚手架提示和变更日志按本次实际调整同步，实际升级问题回填通用清单。
   - 每条验收记录关联平台候选、输入制品、工程基线、执行结果和验证边界，供维护者复核。

## Testing Decisions

- **测试原则**：验证工程使用者可观察到的行为，包括真实制品可解析、工程可构建启动、接口可调用、Shell 可加载、权限与租户隔离符合约定、升级前数据仍可用。避免以模板文本相同、内部函数调用或实现细节代替升级成功。
- **主要测试接缝**：优先复用现有仓库外制品消费与模板冒烟入口。在该端到端流程中加入已发布旧版工程升级场景，以实际打包制品生成或升级工程，再通过业务 HTTP 边界及浏览器运行结果验收。默认工程、IO、storage 是同一升级流程中的不同样例，不新增升级专用运行时接口。
- **已有范例**：沿用制品发布后的隔离消费自检、archetype 生成工程集成测试、模板冒烟和平台主链路 E2E 的组织方式；数据库、Redis、S3 按现有模块共享容器与隔离约定验证；Sub-App 沿用独立宿主及真实 Shell 联邦加载的浏览器验证方式。
- **已确认的接缝**：前述通用升级自动验证、两个试点分别验收，以及默认工程与 IO/storage 数据验证，均已在本次讨论中确认，不追加访谈或扩大兼容承诺。

| 验证场景 | 输入与执行方式 | 必须观察到的结果 |
| --- | --- | --- |
| 新建 Business Service 与 Sub-App | 从当前候选实际制品在仓库外创建工程，复用已有模板冒烟与接入验证 | 依赖解析、构建、相关测试和既有接入链路通过，生成内容与配套版本一致 |
| 已发布旧版工程升级 | 用已发布的 `0.1.0` 制品建立旧工程，按升级清单合并变化并消费候选包 | 升级后构建与业务行为通过，已有业务改动和迁移历史保留；步骤能从固定基线重复执行 |
| 默认工程数据 | 升级前建立已有业务数据，执行本次所需升级后通过业务入口读取和操作 | 既有数据按业务语义保留，升级后正常读写，权限及租户隔离仍有效 |
| IO 可选能力 | 使用可核对历史 IO 源码构建的独立未发布基线，准备已有任务和相关业务数据，执行所需增量迁移 | 既有数据可用，本次相关导入导出及任务行为符合契约，未修改已执行迁移；基线提交及产物来源明确，不冒充已发布制品 |
| storage 可选能力 | 使用独立旧版样例，准备已有文件及业务引用，执行所需增量迁移 | 既有文件和引用按升级契约可用，本次相关存储行为通过，未重复或遗漏所需迁移 |
| Sub-App 两种运行方式 | 对升级后的同一业务前端分别运行独立宿主和配套 Shell 挂载 | 页面和业务请求正常，认证路径、接口入口、共享依赖及主题继承符合约定 |
| lowcode | 在自身升级分支记录实际基线、消费候选制品并进行后端与前端隔离验收 | 提供实际改动、执行结果和验证边界；发现已补入通用说明 |
| ai-platform | 在自身升级分支记录实际基线、消费候选制品并进行后端与前端隔离验收 | 提供实际改动、执行结果和验证边界；发现已补入通用说明 |
| CI 与本地复现 | 对固定基线和候选运行相同升级验证入口，失败时保留诊断材料 | 失败准确使升级验证不通过，本地能够复现；相关检查进入发布质量门 |
| 候选变化 | 对照已有验收记录检查候选提交及制品变化 | 受影响部分重新验证，发布准备结论不会继续引用不适用的旧证据 |
| 版本发布后消费 | 从目标 Maven/npm 仓库只读下载和消费已发布制品 | 制品可被仓库外工程使用；此验证不重新发布或覆盖同版本 |

现有后端、前端和主链路质量门继续执行。测试使用既有可用接缝，不能把 HTTP mock 描述为真实后端联调，也不能把 Outbox 断言描述为实际 Broker 投递；未覆盖范围在交付中如实说明。

发布前的四类证据——新建、通用升级、可选能力、两个试点——均属于发布准备的验收条件。目标制品仓库只读消费复验在版本发布后执行，发布准备交付时明确标记其执行时点，不提前宣称通过。

## Out of Scope

- 自动改写已有业务工程、自动覆盖业务代码或重新生成整个工程的升级工具。
- 任意历史快照组合、自定义模板变体或所有第三方工程的通用迁移承诺。
- `0.1.0` 与 `0.2.0` 长期混合运行、额外的跨版本兼容层及滚动升级机制。
- 将 IO、storage 等可选能力加入默认 starter，或为本次升级引入无关业务功能和重构。
- 替换或改写已执行迁移，清空已有数据库以规避升级问题。
- 在本次发布准备实施中向目标仓库发布制品、执行生产数据迁移或切换环境；这些动作另按发布流程执行。
- 将整个 lowcode 或 ai-platform 产品测试套件迁入平台 CI，或新增与本次升级无关的部署验证体系。

## Further Notes

- 本规格依据 2026-11-17 已确认的八项决策整理，按 to-spec 请求重写并标记为 `ready-for-agent`，可直接作为后续实施拆票依据。
