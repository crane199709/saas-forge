# 08: 升级质量门与发布准备验收

**What to build:** 发布维护者可以使用本地与 CI 一致的入口验证升级，并据同一候选版本的新建、通用升级、可选能力和两个试点证据判断是否发布就绪，同时获得集中、可执行的升级说明。范围以[规格](../spec.md)为准。

**Blocked by:** 02 已有 Business Service 升级与数据保留；03 已有 Sub-App 升级与宿主接入；04 storage 增量升级与已有文件验证；05 IO 增量升级与已有任务验证；06 lowcode 实际升级与隔离验收；07 ai-platform 实际升级与隔离验收

**Status:** ready-for-agent

- [ ] 将服务、Sub-App、IO、storage 的通用升级场景接入现有 CI 与发布质量门，复用已有入口并提供本地复现方法，保留既有后端、前端、主链路和模板质量检查。
- [ ] 升级验证失败时，相应质量门失败并保留足以定位的诊断材料，不以新建工程成功替代已有工程升级成功。
- [ ] 汇总工单 01—07 的输入基线、候选提交、版本、制品摘要和结果，能够核对各项证据是否适用于当前候选。
- [ ] 候选内容变化后识别受影响场景并复验；影响两个试点时更新对应试点证据，记录判断依据，不继续引用不适用的旧结论。
- [ ] 两个试点保持各仓库独立验收，提供本次发布可复核的实际升级结果，不将整个业务产品测试套件迁入平台 CI。
- [ ] 收口统一升级清单，覆盖支持起点、版本含义、依赖与配置必改项、参考工程差异、按能力选择的迁移、验证命令、成功判据和失败处理。
- [ ] 同步受影响的接入指南、规范分发、脚手架提示和变更日志；版本表述区分已发布、候选和待发布制品，不将 0.1.0 或 0.2.0 描述为产品正式版。
- [ ] 明确环境内配套切换要求，保留已有业务代码、自定义配置和已执行迁移，不承诺跨版本混跑或自动改写已有工程。
- [ ] 现有及新增的相关验证通过，交付证据与未覆盖范围完整；必要证据缺失或路径失败时不宣称发布就绪。
- [ ] 提供版本发布后的只读消费复验说明与工单 09 的交接信息。本票不等待 09 执行，不上传版本制品、不切换环境，不能提前声称发布后复验通过。
