# 前端视觉质量整改规格

Status: ready-for-agent

术语以 [GLOSSARY.md](../../GLOSSARY.md) 为准。本规格的决策经 2026-11-14 的讨论确认，共 16 条，逐条记录在第 6 节。本次不换视觉方向，只补视觉层。

**范围前提**：只做 L1（可见缺口）与 L2（可执行的视觉层）。L3（更换视觉方向、重写核心页面组件的视觉实现）另立项，不在本规格内。

## 1. 问题陈述

租户管理员与平台运营（Operator）每天面对这套后台。功能是完整的，但界面传递的信号是「技术验证骨架」：

- 侧边菜单只有文字，没有图标。多层 [Menu](../../GLOSSARY.md) 分组（清单菜单 + 自定义分组）在视觉上无法快速扫读，全靠逐行读文字定位。
- 更具体的是：Business Service 的 [Resource Manifest](../../GLOSSARY.md) 里 `icon` 字段早就存在、已经随 `/iam/auth/access` 下发给 [Shell App](../../GLOSSARY.md)，`demo-service` 的清单里就写着 `"icon": "grid"`——但这个图标**从来没被渲染过**。前端在菜单项类型、导航条目类型、菜单转换函数、布局渲染四处把它逐个丢掉了。这是一处「声明了却永远不显示」的既存缺陷。
- 页面没有数据时，例如 [Workbench](../../GLOSSARY.md) 的待办与未读通知、字典变更历史、成员列表，界面上只有一行居中灰字。用户不知道是「还没有数据」「筛掉了」还是「加载失败」，也没有下一步可点。
- 浏览器标签页里是默认空白图标（三个应用都用空 data URI 占位），没有产品标识。
- `package.json` 没有声明任何图标库；`@forge/ui` 里唯一的一处图标是两段内联 SVG 路径，且注释明确写着「本包不依赖图标库」——这个立场与「侧栏需要 20 个图标」的现实已经矛盾。

同时，这类问题**无法被定位，也无法被阻止再次发生**：

- 仓库没有任何品牌资产（无 logo、无 favicon、无品牌色命名），`themeTokens.primary` 是 Element Plus 默认蓝 `#409eff`。
- [测试](../../GLOSSARY.md)基线有 229 张 [Visual Baseline](../../GLOSSARY.md) 截图，能挡住回退，但挡不住「本来就没做」。
- `@forge/ui` 的视觉约束完全靠口头约定：样式规则只扫 `.vue` 与 `.css`，而该包全部用 `h()` 内联样式，**零机器校验**；`theme.ts` 里的字面量因为不在扫描范围内而天然豁免。
- 主题 token 只有 15 个，间距、字号、圆角、阴影混在一个平坦清单里，没有分层。要加一档间距或一个阴影，只能继续往这个清单里塞。

用户的判断很直接：一个连侧栏图标和空状态都没有的系统，不太像一个值得托付公司数据的成熟产品。

## 2. 解决方案

分两层补齐，都不换视觉方向、不引入外部设计系统、不做品牌体系。

**L1 补齐可见缺口。** 打通菜单图标的完整链路——后端字段已经有了，只补前端丢掉的四层，让 Resource Manifest 里声明的图标真正显示出来；为 Shell Page 内置页补图标；新增统一的空状态组件并替换现有裸占位；给三个应用补一个极简 favicon。目标是让人一眼能扫读侧栏、空页面给出下一步、标签页上有产品标识。

**L2 补齐可执行的视觉层。** 扩充主题 token（只加不改：z-index、第二档阴影、两档间距、字体族），把表格密度定到 40px 行高，并给 `@forge/ui` 建一道机器校验，让「只写主题 token」这条约定第一次真的能被 CI 拦住。语义色不新建，一律沿用 Element Plus。

**不做的事同样明确**：不做 logo 与品牌体系、不做暗色模式、不引入 webfont、不改后端 icon 契约、不做移动端适配。

## 3. 用户故事

1. 作为租户管理员，我希望侧边菜单每一项都有图标，以便我不逐行读文字就能定位到目标页面。
2. 作为租户管理员，我希望菜单分组（清单菜单分组与自定义分组）与叶子项在视觉上有区别，以便我在三层分组里看清自己在哪一层。
3. 作为租户管理员，我希望同一个功能在不同租户、不同登录会话里图标保持一致，以便我不需要重新建立肌肉记忆。
4. 作为平台运营，我希望平台端的侧边菜单同样有图标，以便我在租户端与平台端之间切换时不用适应两套观感。
5. 作为 Sub-App 开发者，我希望在 Resource Manifest 里声明的 `icon` 能被 Shell App 真正渲染，以便我不必为了一个图标去改前端代码。
6. 作为 Sub-App 开发者，我希望写了一个不在白名单里的图标名时看到回退图标而不是白屏或崩溃，以便我的清单不会因为拼错一个词就让整个菜单消失。
7. 作为 Sub-App 开发者，我希望规范里明确列出可用的图标名，以便我不用猜、不用试。
8. 作为租户管理员，我希望列表没有数据时看到一句说明和一个可点的主操作，以便我知道是「还没有」还是「筛掉了」，并且知道下一步做什么。
9. 作为租户管理员，我希望搜索没有结果时看到的提示与「本来就没有数据」不同，以便我不会误以为数据丢了。
10. 作为租户管理员，我希望空状态在 1024 宽度下仍然完整可见、不被裁切，以便我在笔记本上也能看清。
11. 作为租户管理员，我希望浏览器标签页上显示产品标识，以便我在同时开十几个标签页时能认出它。
12. 作为键盘用户，我希望用 Tab 能依次到达每一个菜单项，且侧栏图标不被读屏软件念成无意义的字符，以便我不依赖鼠标也能导航。
13. 作为租户管理员，我希望表格在同样的屏幕里显示更多行，以便我不用频繁滚动就能看完一页数据。
14. 作为租户管理员，我希望表格行高压缩后长文本与操作列仍然不折行、不裁切，以便密度提升不牺牲可读性。
15. 作为平台维护者，我希望新增一个间距档位时不需要改 `@forge/ui` 的每个组件，以便版式调整是局部改动而不是全局搜索替换。
16. 作为平台维护者，我希望在 `@forge/ui` 里误写了字面量色值或字号时被 CI 拦住，以便这条约定不再依赖人的自觉。
17. 作为平台维护者，我希望视觉基线在改动后被一次性重跑并且能看清哪些变了、为什么变，以便我评审时不面对一堆无法解释的像素差异。
18. 作为平台维护者，我希望新加的校验规则不会让仓库外已生成的 Sub-App 工程突然 CI 变红，以便升级不变成外部团队的紧急事件。
19. 作为平台维护者，我希望换主色时仍然只改一处就让全站跟随（含 Element Plus 的派生色），以便多租户主题能力不被破坏。
20. 作为评审者，我希望用固定的一组关键页面做前后对比来判断这次整改是否成功，以便「变好看」有可核对的依据而不是感觉。
21. 作为评审者，我希望空状态、图标、密度这三类改动各自独立可回滚，以便某一项判断错了不牵连其他。
22. 作为接手这个仓库的开发者，我希望知道「主题 token 为什么保留旧名不删」，以便我不会把它们当成技术债顺手清理掉。
23. 作为接手这个仓库的开发者，我希望知道哪些视觉规则是硬约束、哪些只是建议，以便我知道哪些会被 CI 拦、哪些会被评审拦。
24. 作为未来的决策者，我希望这次明确留下了「为什么不换视觉方向」的记录，以便下次讨论 L3 时不用从头论证。

## 4. 实现决策

### 4.1 图标链路

- **打通既有字段，不改后端。** Resource Manifest 的菜单节点已有 `icon`，已随 access 响应下发到前端 SDK 类型。本次只在 `@forge/ui` 与 Shell App 侧补上丢失的四层：导航条目类型增加可选 `icon`、菜单项类型增加可选 `icon`、菜单转换函数透传、布局组件渲染。后端的校验、存储、下发一律不动。
- **图标解析收敛到一个模块。** `@forge/ui` 新增导出：给定图标名返回图标组件。名字同时接受 kebab-case 与 PascalCase，内部归一化后查一张**白名单**，未命中返回默认图标。白名单是唯一的事实来源，约 15–20 个图标，覆盖本次所有菜单项所需。
- **图标对读屏隐藏。** 侧栏图标是装饰性的，语义由紧随其后的菜单文字表达，因此图标本身标记为对辅助技术隐藏，不额外提供 aria-label。
- **依赖显式化。** `@element-plus/icons-vue` 写进 `@forge/ui` 的依赖，版本与 `element-plus` 对齐。这**推翻了**「本包不依赖图标库」的既有立场，需要同步删掉那处注释，并把编辑器里两段内联 SVG 路径改为从白名单取，使图标来源只有一处。
- **Shell Page 内置页手工补图标。** 内置页不在清单里，图标只能按页面语义手写。tenant-app 与 platform-console 的内置页注册表各自补一遍。demo Sub-App 不动。

### 4.2 空状态

- `@forge/ui` 新增空状态组件：可选图标、必填标题、可选描述、默认插槽放主操作。**不做**按场景拆多个变体组件——场景差异由调用方传参表达，多了就会退回「每页各写一套」。
- 列表组件保留现有的 `emptyText` 入参兼容，内部改为渲染该组件，外部调用方不需要改。
- 替换仓库中现存的四处裸 `el-empty`（字典变更历史三处、平台身份面板一处）。

### 4.3 favicon

- 三个应用各补一个极简 SVG favicon：主色块 + 产品名首字母。**不做** logo 体系、不做品牌规范、不新建品牌色命名。
- 明确边界：这是识别块，不是品牌资产。将来要做品牌体系时它可以被整体替换。

### 4.4 主题 token

- **只加不改。** 现有 15 个 token 的名称与取值全部保持原样，不设删除期。理由是仓库外已生成的 Sub-App 工程无法被追踪，任何「一个版本后删除旧名」的承诺都是空头支票。
- 新增：z-index 五档、第二档阴影、间距 32 与 48 两档、字体族一项。字体族显式采纳 Element Plus 的系统字体栈，理由是不引入 webfont——中文 webfont 体积以 MB 计，而所有 Sub-App 共用同一个 Shell，加载成本会转嫁给每个租户。
- **不新增语义色。** 语义色一律沿用 Element Plus 的 `--el-color-*` 与 `--el-text-color-*`。另建一套 `--forge-color-*` 语义色会要求同步维护八个派生色，双源必然漂移，且与既有规范冲突。

### 4.5 密度

- 表格行高定为 40px，正文字号 14px 保持不变。这是「专业克制为骨、借现代精致的密度」的最小落地，不做激进压缩。
- 密度调整会改变几乎所有基线截图，因此必须独立成一个改动单元，且排在其他基线相关改动之后。

### 4.6 强制机制

- 新增一个工具，用 TypeScript 编译器 API 静态扫描 `@forge/ui` 中 `h()` 调用里 style 对象的字面量色值与长度值。不用正则——AST 能区分「style 对象里的字面量」与「注释里的值」。
- 该工具作为独立的 lint 步骤接入前端 CI，**先只在 monorepo 内启用**，不进 `sub-app-kit` 的发布物。验证一个版本周期后再由 kit 依赖它，避免所有外部生成工程同时 CI 变红。
- 不修改既有的 `.vue`/`.css` 样式规则，本次只补 `h()` 这个盲区。

### 4.7 文档与决策记录

- **规则分投，不重复。** 外部 Sub-App 也必须遵守的（图标白名单与回退、空状态用法、密度、五态）进 `sub-app.md`，并按规定走脚手架同步；平台内部的实现细节（token 分层结构、组件接口、基线维护流程）进 `frontend-design.md`。同一句话不在两份文件里各写一遍。
- 新增一份 ADR：主题 token 是三层契约（primitive / semantic / component），并承担微前端样式隔离边界。它同时满足难逆转、事后会问为什么、有真实权衡三个条件——难逆转因为外部工程依赖它，会问为什么因为保留旧名不删看着像技术债，权衡是可读性对零破坏。
- `GLOSSARY.md` 增两条术语：`Theme Token（主题 token）` 与 `Visual Baseline（视觉基线）`，各带同义禁止项，不写实现细节。
- 脚手架同步按实质相关执行：`docs/standards/`、`sub-app-kit` 模板、`CHANGELOG.md` 必更；`forge-service-archetype` 与 `business-service-guide.md` 若确无前端章节，在 `CHANGELOG.md` 写明本次无需变更及理由。

## 5. 测试决策

**什么算好测试。** 只测用户能看到的外部行为：菜单项里有没有图标、图标在文字之前、未知名是否回退、空状态是否渲染出标题与操作、像素是否变化。不测实现细节——不测白名单表的内部结构，只测「传这个名字得到哪个图标」；不测组件内部用了哪个 Element Plus 子组件。

**三条接缝，新增 0 个。**

1. **主接缝（最高点）：`frontend/e2e/visual/` 的 Playwright 视觉基线。** 真实启动三个应用、mock 认证接口、断言像素。L1 的视觉结果全部在这一层断言。用例加进现有 spec 文件，不新建。
2. **组件层：`@forge/ui` 的 Vitest 组件测试**，沿用既有的「按 Shell 方式挂载」辅助函数。只放像素测试不划算的断言：图标名归一化与回退、空状态的 prop 组合、图标元素与文字的先后顺序。
3. **应用单元测试：菜单转换函数。** 断言清单菜单节点的 `icon` 被透传且其他字段不丢。

**为什么不开新接缝。** 三个接缝都已存在且分别覆盖纯函数、DOM 结构、真实像素，正好对应三类断言；新增接缝只会增加维护面。

**已知无覆盖。** favicon 没有任何接缝可以验证——Playwright 截取的是页面内容，不含浏览器标签页。它只能人工确认，这一点在验收时说明，不假装有自动化覆盖。

**既有同类测试可作先例**：`@forge/ui` 的布局组件测试、列表组件测试、Shell App 的菜单转换测试、视觉测试里的导航与租户列表用例、工作台用例。

**基线纪律。** 全部基线必须在同一台 macOS 上一次性重跑；L1 的基线更新单独成一个提交，不与代码改动混，以便评审时能单独看待「哪些像素变了」。

## 7. 不在本次范围

- **L3 更换视觉方向**：重写页面头部、列表页、工具栏三个核心组件的视觉实现，以及由此产生的全量基线返工。
- **品牌体系**：logo、品牌规范、品牌色命名、对外品牌表达。
- 暗色模式。
- webfont 与自定义字体。
- 后端对 `icon` 做枚举或白名单校验（会让既有清单与外部 Service 立刻不合规，属破坏性变更）。
- 导航布局语义变更（新增自定义分组规则、改变分组层级）。
- 移动端适配——只针对桌面宽度设计。
- 授权树与权限树的图标渲染：数据里已有 `icon`，本次不在两棵树里渲染，留作后续。
- 把 `@forge/ui` 的内联样式全面重构为 CSS 文件。
- 仓库外已生成的 Sub-App 工程的升级与迁移。

## 8. 补充说明

**关键事实（本次的出发点）**：`icon` 在后端清单里存在、经 access 接口下发、前端 SDK 类型也有，但前端在菜单转换与布局渲染之间把它丢了。所以「加侧栏图标」不是新建能力，而是修一处既存缺陷——零后端改动、零契约变更。

**三个已知风险**：

1. **白名单会漏。** 外部 Service 的清单可能写任意图标名，未命中就回退默认图标。这是刻意选择（不动后端校验），代价是个别菜单显示为通用图标而不是报错。回退必须在 `sub-app.md` 里写清楚。
2. **基线大面积变化。** L1 改了侧栏与空状态，几乎每张截图都会变。这不影响「只有 5 张用于评审」，但会让 diff 难读，所以基线更新单独提交。
3. **强制工具可能误报。** AST 检查对 `h()` 的写法有假设，遇到不常见的写法可能误判。若误报过多，退路是放宽为只报 warning，而不是退回正则。

**已确认的环境前提**：Python 与 Node 工具链就绪；前端 CI 已有样式检查步骤；视觉基线只在 macOS 生成，团队固定同一平台。

**实施后补充的事实**（2026-11-14）：
